# gremu — план безопасности и запуска на хостинге

Стек: **Vercel** (сайт) + **Supabase** (PostgreSQL, Сингапур) + **GitHub** (код) + Google OAuth, Gemini, (позже) Payme и Resend.
Порядок: сначала **P0** — без этого сайт открывать нельзя; затем **P1** — первая неделя; **P2** — постоянно.

Что уже сделано в коде (не нужно повторять): секреты только на сервере (проверено сканированием), права проверяются на сервере на каждой странице/API, CSRF-защита JSON-API и форм, экранирование XSS, параметризованные SQL-запросы, заголовки безопасности (HSTS, X-Frame-Options, nosniff, Referrer/Permissions-Policy), RLS на всех таблицах Supabase, оплата Payme засчитывается только по проверенному callback, rate limit на формах/AI/входе, журнал действий админки, 39 тестов.

## P0 — до открытия сайта для покупателей

### 1. Сменить все ключи, которые были в переписке
Эти значения попали в историю чата, поэтому считаются скомпрометированными. Создать новые → вписать в Vercel (**Settings → Environment Variables**, окружение *Production*) и в `.env.local` → **Redeploy**:

| Что | Где сменить |
|---|---|
| Пароль базы Supabase | Supabase → Project Settings → Database → **Reset database password** → обновить `DATABASE_URL` |
| Secret-ключ Supabase (`sb_secret_…`) | Supabase → Project Settings → API Keys → удалить старый (сайту он не нужен) |
| Ключ Gemini | aistudio.google.com/apikey → создать новый, старый удалить → `GEMINI_API_KEY` |
| Client secret Google OAuth | Google Cloud → APIs & Services → Credentials → клиент → **Reset secret** → `GOOGLE_CLIENT_SECRET` |
| `APP_SECRET` | для production уже сгенерирован новый (в `.env.vercel`) — использовать его, не локальный |

### 2. Настроить переменные Vercel правильно
- [ ] `APP_URL` = настоящий адрес сайта с `https://` (без `/` в конце).
- [ ] **Не задавать** `AUTH_DEV_LOGIN` и `CATALOG_SEED_DEMO` в production.
- [ ] Переменные с секретами — только для окружения **Production**. Preview-деплои (каждая ветка/PR) иначе работают с боевой базой. Для preview — отдельный проект Supabase или вообще без `DATABASE_URL`.
- [ ] Vercel → Settings → **Deployment Protection**: включить защиту preview-деплоев (Vercel Authentication), чтобы их адреса не были открыты всем.

### 3. Двухфакторная аутентификация (2FA) на всех аккаунтах
Взлом любого из этих аккаунтов = взлом магазина:
- [ ] GitHub (Settings → Password and authentication)
- [ ] Vercel (Account Settings → Authentication)
- [ ] Supabase (Account → Security / MFA)
- [ ] Google-аккаунты владельца и всех сотрудников из `ADMIN_EMAILS` / `STAFF_EMAILS` (вход в админку идёт через них)
- [ ] Регистратор домена, Payme-кабинет, почтовый сервис
- [ ] Использовать менеджер паролей; уникальный пароль для каждого сервиса.

### 4. Вход в админку
- [ ] Перевести сотрудников на вход через Google: вписать их почты в `ADMIN_EMAILS` (полный доступ) и `STAFF_EMAILS` (заказы, обращения, товары).
- [ ] Пароль владельца (`ADMIN_PASSWORD_HASH`) — длинный (16+ символов), нигде больше не используемый: `npm run admin:hash -- "…"`. Это аварийный вход.
- [ ] Не делиться одним входом на нескольких людей — у каждого свой Google-аккаунт (журнал показывает, кто что сделал).

### 5. Google OAuth для боевого адреса
- [ ] Google Cloud → Credentials → OAuth client → **Authorized redirect URIs**: добавить `https://<домен>/api/auth/google/callback`; **Authorized JavaScript origins**: `https://<домен>`.
- [ ] OAuth consent screen → **Publish app** (выйти из режима Testing), указать ссылку на политику конфиденциальности.
- [ ] Лучше отдельный OAuth-клиент для localhost и для production.

### 6. Supabase
- [ ] Supabase → **Advisors → Security Advisor**: убедиться, что нет предупреждений (RLS уже включён на всех 14 таблицах).
- [ ] Сайт не использует REST API Supabase. Можно отключить его совсем: Project Settings → API → **Data API** → выключить (или убрать схему `public` из exposed schemas). Это самая сильная защита от ошибок с RLS в будущем.
- [ ] Database → Settings → **Enforce SSL** — включить.
- [ ] Бэкапы: на бесплатном плане их почти нет. Для боевого магазина — тариф **Pro** (ежедневные бэкапы) и, по возможности, **PITR** (восстановление на любой момент).

### 7. Юридическое (обязательно проверить с юристом)
- [ ] **Локализация персональных данных.** Закон Республики Узбекистан «О персональных данных» (ЗРУ-547, ст. 27¹) требует хранить персональные данные граждан Узбекистана на серверах **на территории Узбекистана** и регистрировать базу в Государственном реестре баз персональных данных. Сейчас данные (имена, телефоны, адреса в заказах) лежат в Supabase в Сингапуре. Варианты: сервер/PostgreSQL у узбекского провайдера (сайт работает с любым PostgreSQL через `DATABASE_URL`) или другое решение по совету юриста.
- [ ] Политика конфиденциальности и согласие на обработку данных (тексты для форм уже есть, нужна сама страница политики).
- [ ] Публичная оферта / условия продажи, политика возврата, реквизиты магазина.

### 8. Контент перед открытием
- [ ] **Заменить случайные цены** у 50 товаров на настоящие (сейчас они заглушки и видны покупателям!) — Админка → Товары.
- [ ] Марка (Hyundai/Kia) и совместимость по каждому товару; проверить 25 спорных номеров (`data/import/gremu-poster-2026-11-conflicts.md`).
- [ ] Контакты, адрес, условия доставки/оплаты/возврата (`src/content/info-pages.ts`, `src/config/shop.ts`).
- [ ] Удалить тестовые данные из боевой базы, если появятся после проверок.

## P1 — первая неделя после запуска

### 9. Защита от ботов и перегрузки
- [ ] Лимиты запросов сейчас хранятся в памяти одного серверного процесса — на Vercel (много экземпляров) они почти не работают. Решение: **Upstash Redis** (бесплатный план) для общих лимитов, или **Vercel Firewall → Rate Limiting** правила для `/api/*` (на тарифе Pro).
- [ ] Vercel Firewall: включить **Bot Protection** / Attack Challenge Mode при атаке.
- [ ] При спаме в формах — подключить CAPTCHA (Cloudflare Turnstile, бесплатно) к контакту и AI-помощнику.

### 10. Расходы и ключи внешних сервисов
- [ ] Gemini: Google Cloud → Billing → **бюджет и оповещения**; ключ ограничить только Generative Language API (APIs & Services → Credentials → ключ → API restrictions).
- [ ] Vercel: Settings → **Spend Management** — лимит расходов.

### 11. Почта
- [ ] Resend: подтвердить домен, добавить записи **SPF, DKIM, DMARC** в DNS (иначе письма уходят в спам и домен легко подделать).
- [ ] Задать `MANAGER_EMAIL`, `EMAIL_PROVIDER=resend`, `EMAIL_API_KEY`, `EMAIL_FROM`; отправить тестовое обращение.

### 12. Мониторинг
- [ ] Uptime-монитор (UptimeRobot / Better Stack, бесплатно): проверка главной и `/ru/catalog` каждые 5 минут, оповещение в Telegram/почту.
- [ ] Отслеживание ошибок: **Sentry** (бесплатный план) или хотя бы регулярный просмотр Vercel → Logs.
- [ ] Раз в неделю смотреть журнал действий админки (`/ru/admin/audit`): неожиданные входы, массовые изменения цен.

### 13. GitHub
- [ ] Репозиторий оставить **Private**.
- [ ] Settings → Code security: включить **Secret scanning**, **Push protection**, **Dependabot alerts** и **security updates**.
- [ ] Settings → Branches: правило защиты для `main` (запрет force-push, удаления).

### 14. Домен
- [ ] Подключить свой домен в Vercel (Settings → Domains), проверить автоматический HTTPS.
- [ ] У регистратора: **Registrar Lock** (запрет переноса), 2FA, при возможности **DNSSEC**.
- [ ] После стабильной работы — `Strict-Transport-Security` с `preload` и подача на hstspreload.org.

## P2 — постоянно / по мере роста

### 15. Обновления зависимостей
Проверка `npm audit` на 2026-11-25:
- **На сервере:** 2 уязвимости в Next.js 15.5 (PostCSS внутри Next — затрагивает обработку CSS при сборке; реального риска для сайта мало, т.к. CSS только наш). Исправление — переход на **Next.js 16** (мажорное обновление, нужно тестирование). Запланировать, прогнать `npm run check` и `npm run test:e2e`.
- **Только инструменты разработки** (vitest, drizzle-kit, esbuild — 2 critical, 4 moderate): на сайт не попадают, но обновить при следующей ревизии (vitest 5, свежий drizzle-kit).
- Раз в месяц: `npm audit`, обновления Next.js (патчи безопасности выходят часто).

### 16. Content-Security-Policy
- [ ] Сейчас CSP ограничивает фреймы, формы и `<object>`. Следующий шаг — полная CSP для скриптов с nonce (защита от XSS второго уровня). Требует правки middleware и проверки GSAP/Three.js.

### 17. Платежи (когда будет договор с Payme)
- [ ] Только после тестов в песочнице (`docs/PAYMENTS.md`): боевые `PAYME_*`, endpoint в кабинете, фискализация (коды ИКПУ).
- [ ] Ключ Payme — только в Vercel, никогда в коде или чате.

### 18. План действий при инциденте
1. **Откатить сайт:** Vercel → Deployments → предыдущий рабочий деплой → **Promote to Production** (мгновенно).
2. **Сменить ключи** (таблица в п.1) и `APP_SECRET` — это разлогинит всех и сделает старые ссылки недействительными.
3. **Отозвать доступ:** убрать email из `ADMIN_EMAILS`/`STAFF_EMAILS` → Redeploy; Supabase → удалить подозрительные сессии из `user_sessions`.
4. **Проверить:** журнал действий админки, Vercel Logs, Supabase Logs.
5. **Восстановить данные** из бэкапа Supabase при необходимости.
6. Записать, что произошло и что изменено.

### 19. Регулярные проверки
- Ежемесячно: `npm audit`, обновления, Supabase Security Advisor, кто есть в `ADMIN_EMAILS`/`STAFF_EMAILS`.
- Ежеквартально: смена пароля владельца админки, проверка бэкапа (тестовое восстановление), экспорт каталога в CSV как резервная копия.
